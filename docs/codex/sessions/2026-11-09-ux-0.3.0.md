# Prise en main et portable 0.3.0

## Périmètre

La version 0.3.0 ajoute un accueil avec démonstration manuelle, création et reprise de projet ; un constructeur de circuits et de transferts ; des diagnostics qui ouvrent le champ à corriger ; une revue globale des associations ; un import CSV avec aperçu ; un explorateur OPC UA de métadonnées ; l’annulation et la récupération des brouillons ; un lanceur Windows avec arrêt et mise à jour guidée.

Les fichiers principaux sont `App.tsx`, `Welcome.tsx`, `Readiness.tsx`, `draftStore.ts`, `TransferBuilder.tsx`, `processCircuits.ts`, `GlobalBindings.tsx`, `MappingImport.tsx` et `OpcUaBrowser.tsx` dans `frontend/src/`. Le serveur expose les trois aperçus dans `fat_studio/app.py` ; l’exploration est isolée dans `fat_studio/opcua_browser.py`. Le cycle du portable est dans `scripts/portable-launcher.py`, `portable_host.py`, `portable_window.py` et `portable_update.py`.

Les formats projet et scénario restent en version 1.0. La découverte lit les métadonnées sur une cible autorisée, après contrôle de son identité. Aucun NodeId ni profil analogique n’est déduit d’une adresse Siemens. Les propositions de mapping et de circuit modifient un brouillon ; une sauvegarde explicite reste nécessaire. Les observations et verdicts humains restent saisis par le testeur.

## Reproduire les vérifications

Depuis une copie source avec les dépendances verrouillées installées :

```powershell
python -m ruff check fat_studio integrations tests scripts public_distribution.py build_public.py
python -m pytest
```

Dans `frontend/`, exécuter `npm ci`, `npm run build`, puis, à la racine, `python scripts/build-web.py`. Exécuter ensuite **`npm test`** dans `frontend/` : `npm run test:e2e` ne couvre qu’un fichier de tests. Les serveurs navigateur utilisent des données temporaires. Ne jamais définir `FAT_E2E_BASE_URL` vers une instance qui contient des essais utilisateur.

Les nouveaux tests navigateur couvrent le premier essai, les transferts réels et leur conservation de volume, la duplication sans adresse PLC, les propositions ambiguës, la fusion CSV, les erreurs de connexion, l’annulation et les brouillons par projet, révision et dossier. Les tests Python couvrent l’exploration asyncua, les refus de contexte et d’identité, l’absence d’écriture, les limites du transport, le cycle du lanceur et la vérification des mises à jour.

La [release 0.3.0](https://github.com/vandervan0001/Vanguard-FAT-Studio/releases/tag/v0.3.0) contient le reçu de vérification du portable, son commit source exact et son SHA-256. Ce reçu distingue les résultats locaux, la CI et les essais sur le runtime embarqué. Les tests locaux ne qualifient pas une cible Siemens et n’attribuent aucun verdict FAT humain.

## Construire et reprendre

Suivre [INSTALLATION.md](../../INSTALLATION.md) pour construire la wheel et le portable depuis une source Git propre. La sélection reste explicite dans `public-distribution.json`. Les dossiers `.local/`, `.dev-loop/`, données d’essais et notes de travail privées sont exclus des paquets.

Le manifeste du portable indique la version, le commit et l’état des sources publiques. Construire vers un dossier neuf, contrôler le manifeste avant et après les essais, puis vérifier le ZIP final et son téléchargement. Ne pas modifier une livraison scellée.

Les parcours et limites sont décrits dans le [guide utilisateur](../../USER_GUIDE.md), le [guide du lanceur](../../PORTABLE_LAUNCHER.md) et le [contrat CLI/API](../../AI_CONTROL.md). Toute reprise commence par l’état Git courant ; une preuve historique ne remplace pas la vérification du nouveau diff.
